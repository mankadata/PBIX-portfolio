How it is built

The HTML is only the last step, the drawing. Everything underneath it, the loading, the model and the measures stayed in Power BI.

Data

The data comes from the FAOSTAT REST API, not from an Excel file or a folder of CSVs. Power Query handles it in four parts: a Config record holding the endpoint, the item code and the year range; fnLogin, which exchanges credentials for a bearer token; Auth, which runs it once; and fnFAOSTAT, which takes a domain and a list of element codes and returns a typed table.

Tokens expire after 60 minutes and the API has no refresh endpoint, so a 401 triggers a fresh login and one retry.

Modelling

Two fact tables, Production and Trade, share the Countries and Year dimensions, with a few disconnected tables for the field parameters.

The measures live in a _Measures table, written in the DAX query view with comments, so they can be read and reviewed like code.

Visuals

The visuals on the Production and Trade pages are HTML and SVG generated inside DAX measures.

A custom theme JSON drives every native visual. The HTML visuals carry their own colour constants, and I keep the two in sync by hand, which is the first item on the list below.

What HTML visuals do not solve

Custom HTML visuals are popular right now, and the screenshots look great. People talk much less about the limits. My problem with a full HTML dashboard is not how it looks, it is that you cannot see what sits behind it. Here is what it does not solve, because all of it applies to this report too, and I knew about it when I started.

They cannot filter the report back.

An HTML visual gets filters, but it cannot send one. Click a bar in the waffle chart and nothing else on the page changes. The more of the page you give to HTML, the less the report works as a tool you can explore, and the more it becomes a poster.

This is the strongest argument against the approach, and it is why the map here stayed a native visual.

Accessibility is almost completely missing.

Screen readers cannot read inside the visual's iframe, and you cannot move through it with the keyboard. The alt text measures in this model help a little, but they do not fix it. In the public sector, or in a regulated company, this alone can stop the whole idea.

It cannot be certified.

To be certified in AppSource, a visual must not write raw input into the page and must not call out to the internet. That is exactly what an HTML visual does.

Certification is what makes two things work: export to PowerPoint, and the image that goes out with an email subscription. Neither works here. An administrator can also allow certified visuals only, or turn custom visuals off completely — and then the report does not run at all.

Buying your way out has a price of its own.

AppSource has visuals that solve a lot of this. I was not always happy with them, and some of the good ones want a subscription before the watermark disappears. Price and certification are separate questions: a visual can be certified and still cost money.

And in a company, the decision may not be yours at all — the policy can simply forbid installing anything.

Someone has to maintain it, and that means documenting it.

There is no formatting pane. With a native visual the settings are visible to anyone who opens it; with a visual drawn in DAX, nothing is visible anywhere. The next person who opens this file has to read several hundred lines of HTML, CSS and SVG inside DAX text, so I wrote comments throughout.

That person has to be an advanced DAX reader and a BI developer at the same time, which is a much narrower hire than "someone who knows Power BI". AI can help write the documentation, and I think that is a fair use of it: the decisions are mine, the AI described them.

Documentation matters everywhere, not only here. I once took over a report that did not contain a single line of HTML, and it still felt like forever before I understood what was happening in it, and why it had been built that way. There was nothing written down, not even the stakeholder requests — so I was missing more than the logic, I was missing the intent. Documentation is not an extra, it is a basic condition.

Debugging is blind.

Every HTML visual is an iframe with its own render cycle, and there is no developer console. If a text concatenation breaks, you get an empty box, not an error message.
